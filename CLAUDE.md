# psephos

A monitor for the erosion of voting rights across four channels of federal pressure: legislation, executive action, litigation, and the administrative coercion in between. The full build spec is imported on the next line.

@docs/psephos.md

## Workflow (non-negotiable)

Spec-driven and review-gated. Use /plan to propose a plan and wait for approval before writing anything. Use /diff to show changes before any commit. No commits without a shown diff.

**Readers launch blind** (Corey, standing rule, 2026-10-03).
- A reader's whole start message is `tools/reader_launcher.txt`, rendered for its lens and its file by `python -m tools.reader_launch render`. The file is staged under its own content hash (`stage`), so its path names nothing.
- Launch readers with the Agent tool, never the Workflow tool. The Workflow tool hands every agent the turn's user message verbatim, so a review brief reaches the readers.
- Briefs from the review side go to the main session only.
- Every run starts with a canary on an empty file and ends with `python -m tools.reader_launch check`. The check fails the run when a reader's start message is not the launcher, anything else reached it, or it did not see every line of its file. Its record goes in `docs/reads/`.

**A branch with work on it gets a docs/status.md line in the session that creates it** (Corey, standing rule, 2026-10-02). `r1-switch` sat built, reviewed and unrecorded for two days, and the next session began rebuilding it. Name the branch and its commits by subject: `tools.sha_sweep` treats a sha only a local branch can reach as an orphan.

## Conventions

- Conventional commit messages. Git identity and repo under CSU-J3.
- Secrets live in GitHub Actions secrets and a local .env, never in the repo: CONGRESS_API_KEY, COURTLISTENER_TOKEN, and LEGISCAN_API_KEY (all three active), plus TURSO_DATABASE_URL and TURSO_AUTH_TOKEN for the remote database.
- **Every issue body is scrubbed before it is posted (unit 99, 2026-09-28).** Actions masks secrets in the run log, not in what a step sends to the Issues API. `scrub.py` is the one scrub (query strings dropped, every credential in the step's env and the Turso host replaced, standard library only), and every step that comments on or opens an issue runs `python3 "$GITHUB_WORKSPACE/tools/scrub_issue_body.py" FILE` on its body with its run's credentials in its env. `tests/test_issue_body_scrub.py` fails a posting step that skips it; a new lane that posts must scrub.
- **Secret audits (standing rule, handoff 98b §7, 2026-09-24).**
  - **Search by variable name, or compare a sha256 prefix of candidate tokens against a prefix of the value.** Output file paths, counts and hash prefixes only. Never match on the value itself (`rg -F "$KEY"`, `git log -S"$KEY"`): a value on a command line is in flight, visible to any process listing. Never snapshot a process list (`ps`, Task Manager, `Get-Process` with command lines) while a command carrying a secret may be running.
  - **Run secret audits inline, never through subagents or multi-agent workflows.** Their logs capture every command and tool output, the surface the CBT exposure landed on.
  - **Stay inside the repos and services the brief names.** "Anywhere" means the project's own surfaces, not the user folder, the registry, the Recycle Bin or a mail cache. If a brief names no boundary, ask for one rather than choosing the widest.
  - **A clean result proves nothing without a positive control.** Run the same method on a file known to hold the value, and report its match.
  - **Why:** a CBT-session subagent ran `ps -ef` while a LegiScan call was in flight and wrote the key into its JSONL log (since scrubbed). This project's own handoff-98 leak checks matched on the value, which is the same exposure class; no process list was captured.
- POSIX paths in anything the workflow touches; the cron runs on Linux.
- State collector gate order (`collectors/state.py`): `election_match` runs BEFORE the change-hash gate, so `state_seen` only ever holds filter-passers. A term broadening therefore SELF-STAMPS on the next state run — the newly-matched bills have no stored hash, so they pass the gate and get a getBill — and needs no getBill backfill. **Since the session cadence (handoff 98b) that holds for ADJOURNED sessions only because their done-marker (`state_sessions.masterlist_hash`) carries a fingerprint of the filter — terms, exclusions and `election_match`'s source — so any filter change re-polls each adjourned session once (~14 master lists).** Active sessions self-stamp on the next Tue–Sat slot as before. Do not drop the fingerprint to "simplify" the marker: the review of that build reproduced the broadening silently missing every adjourned state without it. (The 5b-a 1,248-item backfill was a different job: linking pre-existing items to the new dimension, not stamping new bills.)
- `tools/` vs `scripts/`: read-only offline analysis lives in `tools/` (`masterlist_corpus`, `sasts_dump`, `sasts_join`, `lit_resolve_audit`, `status_audit`, `coverage_audit`, `scrub_issue_body` (the one scrub, run by every issue-posting step on its body), `recheck_flags` (2026-09-29: order-like entries on a gate-listed docket above that docket's `record_read` watermark in docs/gates.yaml, and on a docket cleared by a no-claim-order reason filed after its read-through date; coverage_audit section 9 reports them and audit.yml comments new ones on the standing "recheck flags" issue, never turning a run red), `merge_notes` (the R1 switch's figures, read once at the switch into `web/lib/entry-merge.json` as dated moves; it re-reads every move from scratch, so a later move such as a new tier-2 link batch must APPEND its own, recorded when it links, never re-run it over the switch's), `reader_launch` (2026-10-03: renders the fixed reader launcher and checks every read run against it, records in `docs/reads/`), and `collect_verdict`, unit 99's scheduled read: `collect.yml`'s Verdict step, which turns a run red on a loud `channel_runs` row, a stale receipt or a data commit that never reached origin (the commit step's marker, 2026-09-30), and writes nothing); anything that mutates a database lives in `scripts/` (`backfill_state_bills`, `backfill_supersession`, `backfill_case_state`, `repair_latest_entry`, `rekey_slug_cases`, `backfill_appeal_metadata`) and is dry-run-by-default with an `--apply` gate. **One carve-out on the `tools/` side (handoff 98, 2026-09-23):** `masterlist_corpus` and `sasts_dump` call LegiScan, so they read the Turso `legiscan_usage` ledger, refuse when their declared worst case does not fit the month's headroom, and write their attempts back to it. That row is the only database write a `tools/` file makes. It records spend against an allowance the cron shares, not a change to the record, and it needs Turso (`collectors.state.open_ledger`). **Four of the six are one-time and already applied — do not schedule any of them.** **`write_heartbeat` (2026-09-17) is the seventh file there and the one exception to both halves of that sentence: it IS scheduled — `collect.yml`'s final step, four times a day, `if: always()` — and it carries no `--apply` gate.** It is not a migration. on "next dev". Other Next apps run on this Windows box and will be killed
too. Scope to this project's port only:

    netstat -ano | findstr :3001
    taskkill /PID <pid> /T /F

pinned, and pin any new script that spawns a dev server — CBT holds
